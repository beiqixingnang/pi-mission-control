# 仓库开发协作

在已授权范围内持续完成交付，减少无效等待、中转和重复验证。按当前项目规则处理软件、硬件或文档仓库，不把某个项目的目录、分区和构建约束推广到其他仓库。

## 先确定当前边界

读取最新用户指令及与本次交付相关的项目规范、有效计划、已有成果和工作区状态。用户当前明确指令优先；本 skill 不产生额外授权，也不解除插件的权限、预算、工作区或运行状态约束。

区分讨论、只读审阅、规划、实施和收尾。只读请求不启动实施或产生项目修改；用户明确要求的暂停、取消、恢复或计划编辑分别执行。询问进度、原因或改动理由本身不构成停工或恢复指令，回答后继续原有授权工作。

## 正常工作流程

1. **明确交付。** 确定结果、文件或批次、负责人、依赖和验收条件。未知范围先做有边界的盘点；已知完整范围先登记，范围改变时留下原因，不静默改变进度分母。简单修改直接完成。
2. **选择相称分工。** 单人能直接完成的任务保持单人。需要并行时按独立文件或批次划分，一个文件有明确写入负责人；执行者负责方案细化、实现、必要验证、自审、证据和常规修复，主模型负责标准、协调和集中验收。
3. **连续执行。** 在有意义的交付边界保存结果。已有逐节目标时按节提交；普通任务按文件或批次提交。成员提交待验收后继续已分配范围，不等待例行确认；在自然批次边界结算任务，便于验收并由原成员接续。
4. **按改动验证。** 选择支撑验收条件的真实入口及必要正反例，复用仍有效的结果。相关源码、共享实现、标准变化或新失败出现后再增量验证，不为每次汇报重跑矩阵。
5. **集中验收。** 区分执行完成、提交待验收、正式接受和提交推送。核对当前目标版本与证据适用范围；具体缺陷交回原负责人，通过部分保留，仅重开受影响部分。
6. **完成并停下。** 交付已授权的全部结果，满足已有发布条件时直接按授权提交推送。说明未覆盖范围和真实限制；局部阻塞时继续独立工作，不以阶段汇报代替后续执行。用户要求完成后停止时，不自动开启其他任务。

## 全程遵循

- 普通实现选择、工具使用、顺序和范围内增量修复由负责人决定。只有缺失的业务范围、验收取舍或外部操作授权才交用户决定；先完成不依赖答案的工作，提供可审结果和具体依据，不重复确认已有授权。
- 使用当前插件已暴露的能力；主模型与成员的工具可能不同。派工前核对所需实际能力，不能凭角色名推断，也不反复调用发现接口查询已知且未变化的工具。
- 新增路径前，核对当前仓库的父子目录公式、大小写、单复数、封闭目录、固定文件名和新增文件范围；通用工具示例不能代替项目命名要求。
- 保留用户及其他执行者的已有修改，遵守文件所有权和只读范围，不以清理工作区、格式整理或消警覆盖他人成果。
- 保持文件角色、公开接口、求值时机、架构入口和输出行为；结构整理不暗中改功能或增设框架。规范与计划的修改授权分别核对。
- 临时资料按项目规则存放。已接受证据保留稳定快照，后续日志另存；存证规模与改动相称，不另建必填进度系统。
- 沿用用户约定的汇报周期。普通成功静默保存，真实失败及范围、权限冲突及时升级；周期核验直接读取已有结果，不例行打断成员、催更或轮询。
- 重载、断线、取消或超时后先检查已有结果和真实执行状态，再决定下一步。状态不明时按插件当前恢复指引处理，不能盲目重放命令。
- 未执行、未知、失败和仅提醒事项如实呈现。成员成功、静态通过或证据字段齐全均不代表整个目标、真实产品或人工验收完成。
