# 协作与集中验收

在需要团队、多个叶目标或持续执行的任务中读取。本文件说明工作方法；工具签名、状态和约束以当前 Mission Control 为准。

## 规划和派工

主目标表达最终交付，阶段组织成套结果，代码叶目标明确到文件或批次；用户明确要求逐节治理时保留对应小节目标。已知完整范围先登记；未知范围先做独立的有界盘点。单次接口容量有限时分批登记，不把接口批次变成新的业务阶段。

可选执行计划记录方法、边界与验证选择。更新方法不改变验收标准；标准变化要更新受影响的具体目标并保留历史。成员可按授权编辑执行计划，不能据此扩大范围或替负责人验收。

派工时一次给清：交付范围及目标关联、文件所有权、不可改范围、接口约定、必要验证、证据去向和批次结束条件。说明约束和预期结果，留给执行者实际设计空间。按任务需要提供读写、执行、证据保存和直接讨论能力；审查职责不自动意味着只读。

相关负责人直接讨论共享接口和具体缺陷。主模型处理标准、所有权及跨批次取舍，不转述双方已有的普通对话。不默认另设监督者，也不为每个小问题重建团队。模型、人数和思考强度按用户本次选择，优先复用合适的成员；无需继续接续的身份再关闭。

## 多目标关联和成员工具

- 主模型用当前派工接口关联任务实际覆盖的叶目标；支持多个目标时优先使用原生多目标关联，超出容量时由同一负责人按有意义的批次连续执行。
- 成员侧若暴露 `goal_context`，用它读取已分配目标；若暴露 `goal_submit`，用它登记该目标当前版本的待验收证据。主模型侧使用 `goal_accept` 正式接受。名称仅说明角色分工，实际可用工具和参数以本次列表为准。
- 单目标任务仍可正常使用单目标关联。工具无法覆盖全部范围时，明确任务关联与实际工作清单，采用受支持的分批方式；不把未关联目标冒充已提交，也不通过配置或脚本绕过关联守卫。
- 缺少目标定义编辑或最终验收权限通常不阻塞实现。已有合法提交通道时继续工作；真正无法读取要求、写入负责文件、验证或登记交付时，记录具体拒绝并在授权内修正能力或分工。

## 持续执行、提交和结算

已有逐节叶目标的任务：完成一节、做相称验证、保存证据并提交待验收，接着做剩余节。普通任务按文件或批次提交，不为了采用本流程额外拆成小节。

提交不等于结束任务，结束任务也不等于目标已接受。在派工时选择自然结算边界，例如一个独立文件或完整关联批次；完成其实现、必要验证、自审和交付说明后正常结束。主模型验收已结算部分，再由原成员继续剩余批次，保持文件所有权。

若插件不允许接受仍有相关执行的目标，保留提交，等自然结算；不为整点汇报强行取消成员。避免把一个永不结算的长任务关联全部后续工作，导致已完成部分也长期无法接受。

## 集中验收和反馈

按约定周期读取已有插件提交、任务结果和证据。`progress.md` 可作简短索引，不成为另一套必填台账。不例行催更、索要额外报告或逐项唤醒主模型。

| 情况 | 后续动作 |
| --- | --- |
| 结果支持当前验收条件且执行已满足结算要求 | 接受准确目标版本并保留证据 |
| 发现具体缺陷或相关证据不足 | 一次说明缺陷、对应标准和补证范围，交回原负责人 |
| 仅有范围外产品违规或未运行门禁 | 记录实际限制，按当前接受标准判断，不擅自扩为修产品任务 |
| 源码、标准或证据已变化 | 先确认影响范围，仅更新相关接受记录 |
| 真实业务取舍尚无授权 | 给用户具体选项和证据，同时推进独立部分 |
| 权限、运行状态或工具故障 | 使用插件当前配置与恢复机制，不伪装成业务审批 |

用户问进度或原因时先简短回答事实，再继续授权工作。只有明确要求暂停、撤销、等待决定，或独立约束确实阻止执行时，才停止相应范围。用户指定主模型亲自写作或实现时，主模型承担该部分，不擅自转交。
