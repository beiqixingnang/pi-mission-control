# Pi Mission Control v2：可行性与重写方向建议

日期：2026-10-17，Asia/Shanghai。状态：**讨论建议，尚未作为已确认的实现方案**。依据为 [固定版本机制调查](../research/2026-10-17-agent-mechanisms/README.md)。本文件记录这一轮关于可行性、保留或重写、TUI方向的判断；没有开始替换业务实现。

后续用户已授权实现，并新增原生Pi能力兼容和运行核心自动维护的约束；实际规格与当前范围见 [v2 PRODUCT](mission-control-v2/PRODUCT.md) 和 [TECH](mission-control-v2/TECH.md)。本文保留最初建议，不把其概念侧栏图当作已实现界面。

## 1. 判断

用户关心的功能集合具备以 Pi 插件产品形式实现的可行性。建议在当前仓库开发 v2，重写运行核心、持久状态协议和 TUI；保留仓库历史、研究材料、原始会话证据，以及经重新核对的少量独立工具。

这里的“可行”指复现明确的功能行为，不是把 Codex、DSH 的全部代码、所有平台安全属性和桌面能力逐项原样搬入 Pi。各项目自己的目标、协议和进程模型不同，完整逐项等价需要另行定义范围，也没有取得 Codex 桌面全部内部源码。

代码量小降低了重写成本；主要工作仍是澄清生命周期、权限、交付语义和故障恢复，并通过验证建立长期可靠性。不能根据新代码文件少就承诺很快达到成熟产品的稳定性。

## 2. 哪些可以用插件实现，哪些需要宿主组件

| 功能 | 可行的承载方式 | 需要明确的边界 |
| --- | --- | --- |
| 独立压缩模型、分块摘要、摘要失败保留、上下文选择 | Pi压缩/上下文扩展点，独立摘要调用与持久产物 | 必须按摘要目标的窗口和请求预算选范围，不能只把整份大prompt换个模型发 |
| 短任务子智能体、持久团队、成员通信、任务树 | 插件注册工具，管理SDK/RPC成员和任务状态 | 会话身份、任务尝试、进程实例、消息投递要独立；成员恢复不等于副作用可自动重放 |
| 主会话结束回合、成员完成后开新回合 | Pi的terminate/生命周期事件及显式trigger API | Pi宿主仍活着时可用；消息入队、追加和实际处理必须分别跟踪 |
| Goal、预算、运行中进度检查 | 共用任务状态和明确的目标续跑资格 | 用户暂停、provider失败、等待子任务和任务完成不能共用含糊状态 |
| 一次性与周期调度 | 持久调度记录加活动宿主中的调度器 | 关掉Pi后仍要执行，需要继续存活的本地运行服务及明确的系统启动方式 |
| 工具权限、只读/可写路径、审批与能力继承 | 工具执行端统一检查，命令/网络/凭据权限独立表达 | 隐藏工具或给prompt写root都不能替代执行点检查 |
| 系统级沙箱 | 插件统一配置和调用原生runner、容器或受支持的外部执行后端 | 单靠TypeScript路径检查无法提供与OS沙箱等价的强制约束；不同平台必须单独验证 |
| 联网搜索、抓取和引文 | 可替换的搜索/fetch工具适配器，也可组合现有插件 | 搜索凭证、远端网络访问和成员工具授权要明确；不能假设任意模型API都有原生搜索 |
| TUI与会话复制/导出 | Pi官方UI扩展接口、公开文本投影与流式导出 | 必须确认布局API支持范围；不能把巨型完整历史一次字符串化 |

因此建议的产品形态是一个统一安装和配置的插件包，内部按职责拆分。它可以包含Pi接入层、本地运行核心、执行后端和持久数据，而不要求用户手工理解十个相互触发的扩展。

本地运行核心是否必须成为独立常驻进程，取决于是否要求关闭Pi窗口后仍运行成员、投递提醒和恢复任务。这一项应在正式规格中明确。若要求成立，独立服务具有直接的需求依据；若只要求Pi存活期间工作，进程内运行核心也值得评估。本文不提前决定daemon、数据库或IPC的具体技术。

## 3. 为什么建议重写运行核心

### 3.1 问题集中在状态协议，而不只是几个函数

现Team、Goal、Supervisor分别维护pending、结果、唤醒条件和timer。普通通知、Goal收割、恢复扫描又使用不同的确认方式。修补某个分支会改变另一个模块的行为：例如peer任务开始被监督器看成即时检查机会、普通通知写入会话但live ACK监听不到、Goal先ACK再请求下一回合。

这些是跨模块语义问题。继续沿现有结构补条件，仍需要同时重新定义多个状态拥有者和提交点；这部分工作本身已接近重写核心。详见调查 [子智能体与交付](../research/2026-10-17-agent-mechanisms/01-delegation-lifecycle.md) 和 [Goal/调度](../research/2026-10-17-agent-mechanisms/04-goal-scheduling.md)。

### 3.2 安全边界应从执行入口重新建立

当前host模式选中了未经workspace路径包装的Pi原生文件工具与bash，root/access仍存在于metadata中，不能由此判断受限程度。模式还涉及父环境继承、成员再派工、进程树取消与Podman写回。只修改界面标签或加prompt无法弥补这些边界。

v2需要先确定每一种执行能力究竟由谁强制、哪些属于明确的host信任等级；再决定复用哪个backend。详见调查 [隔离与权限](../research/2026-10-17-agent-mechanisms/02-isolation-permissions.md)。

### 3.3 原持久化和恢复模型不宜继续沿用

98.2458%的主日志来自重复roster/Goal快照。完整任务树、结果与成员定义反复附着在对话日志中，既放大存储，也增加恢复和导出成本。旧成员恢复、活动任务恢复和消息重投又不是统一事务。

新运行核心应先确定权威状态、增量变化和大产物的存放关系，再提供模型和UI所需的有限视图。具体使用数据库还是增量日志加checkpoint，留待实现方案选择。

### 3.4 原测试不能整体作为新系统验收标准

现监督器测试明确期待job-start之后几十毫秒内发检查，正好固化了违背用户期望的行为。保留测试文件作为历史和用例线索有价值，但“旧测试全过”不能证明新需求满足。应从用户需要的行为重新定义验收，再复用合适的fixtures和底层检查。

## 4. 保留与重写的建议范围

| 资产 | 建议 | 理由 |
| --- | --- | --- |
| 仓库、Git历史、许可证、研究文档、固定来源清单 | 保留 | 有利于追溯和继续维护，不必另开仓库丢失历史 |
| 原始会话、成员session与历史交付证据 | 保留，只读迁移/索引 | 用户历史不能因为重写而丢失；旧活动任务不能盲目恢复执行 |
| 现Team/Goal/Supervisor之间的状态及唤醒协议 | 重写 | 多重状态拥有者和提交点是核心问题 |
| 成员运行、取消、恢复和权限执行链 | 按新语义重写；后端独立评估复用 | host/受限路径、进程树与未知结果需要统一表达 |
| compaction-model的独立选模入口和配置习惯 | 保留有用的接口思路，改写执行流程 | 独立选模有效；单次大请求、截断检查和静默回退仍有局限 |
| 路径规范化、终端控制符过滤、显示宽度等小工具 | 经独立核对后复用 | 低耦合功能有价值，但必须满足新执行边界 |
| 旧TUI状态和布局实现 | 重新设计和实现 | 展示模型依赖旧事件与模糊状态，不适合只换皮肤 |
| 角色预设与协调提示 | 依据明确工作流重写或精简 | 不能用大量提示词补偿执行能力和任务协议不足 |
| 旧测试 | 保留历史与fixtures，重新判断断言 | 避免把原有错误行为继续固定下来 |

建议采用同仓库v2替换的方式。旧代码继续由Git历史和本地基线保留，后续实际切换应有清楚的停机、状态检查与迁移行为；本轮不删除或切换当前安装。

## 5. TUI重新设计方向

TUI应由运行核心的权威状态派生。显示“执行中”要有对应的活动任务与执行实例；“等待”要显示原因和下一次有效触发条件。界面计时和动画不能独立推断任务活着、已消费交付或目标已恢复。

### 5.1 宽屏布局

主对话保持主要空间；顶部或底部保留稳定的目标摘要，右侧显示团队和当前任务。以下为概念示意，数值不是当前真实状态：

```text
目标：完成当前开发阶段          等待团队 · 下次进度检查 27分
┌─ 主对话 ─────────────────────┬─ 团队与任务 ───────────┐
│ 用户指令、阶段交付、裁决结果   │ CPU执行员  正在运行测试 │
│                              │ CPU监督员  等待执行结果 │
│                              │ GPU执行员  修改实现     │
│                              │ GPU监督员  复核证据     │
│                              ├───────────────────────┤
│                              │ 待裁决 1 · 待授权 0    │
└──────────────────────────────┴───────────────────────┘
输入指令…             常规进度已汇总 · 可查看任务、日志和交付
```

成员列表采用稳定顺序、可手动选择，不自动轮播。任务树能够展开，避免“监督员空闲”掩盖它已派出的下游任务仍在执行。模型、执行后端和权限等级可在详情查看；普通页面不堆taskId、deliveryId、ACK状态等内部字段。

### 5.2 状态与通知

- 主会话明确区分生成中、等待团队、等待用户、已暂停、恢复失败；不把全部都画成运行spinner。
- 成员详情区分模型请求、工具/命令执行、等待下游、等待授权、已停止，以及运行状态未知。
- 常规进度合并更新状态区；阶段结果进入交付列表；需要总裁决、权限或真正阻塞时显著提示。
- 目标显示验收条件完成情况、预算及下一次计划检查，不根据聊天次数或时间生成虚假的完成百分比。
- 结果详情可跳转公开对话、原始工具输出和产物。内部推理/签名不作为默认可见内容。
- 停止当前主回合、取消单任务、停止团队分别有清楚作用范围；返回详情界面的按键不应意外停止所有后台任务。

### 5.3 窄屏与Pi接口边界

窄屏使用紧凑摘要和可展开面板，保证输入框与主对话可用；详情通过独立视图查看。宽屏右栏不应靠未经确认的私有布局字段长期维持。

Pi 1.3.0公开扩展类型提供widget、footer、header、custom组件和终端输入等入口，见 `vendor/pi-1.3.0/packages/coding-agent/src/core/extensions/types.ts:147–208`。当前侧栏代码会读取layoutRoot并替换布局，见 `extensions/agent-monitor/layout.ts:7–20`。正式UI方案应先核对布局入口的稳定性、resize/focus/输入/取消语义，再决定固定侧栏、可展开面板或其他公开API方案；如果某个精确布局做不到，应明确记录宿主接口缺口，不能承诺任意改造Pi内置TUI。

## 6. 进入实现前还要决定的事项

后续正式规格应明确：Pi退出后的存活要求、优先支持的Windows/WSL等执行环境、默认执行信任等级、Goal恢复权限、紧急通知条件、大输出与摘要模型预算、以及TUI的主要交互。然后定义状态转移和可观察的验收场景，再决定代码模块与技术选型。

这一顺序延续用户约定：源码机制已经调查，当前讨论取舍，下一阶段形成实现计划；编写和运行测试在其后进行。
