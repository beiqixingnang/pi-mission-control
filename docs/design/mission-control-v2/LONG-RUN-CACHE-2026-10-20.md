# 2.5.0 长任务、笔记维护及缓存修复

日期：2026-10-20，UTC+8。生产会话仅只读检查；故障注入使用专用WSL Pi会话和合成源码。

## 已确认的故障

三个长成员先遇到上游SSE损坏，随后Pi输出的agent_end包含本轮累计消息。旧RPC读取器把所有单行都限为8 MiB，因而在16:48–16:53终止CPU-B、storage和GPU。笔记换窗减少模型上下文，并不保证底层执行回合累计事件也缩小。修复按Pi的type-first线协议流式跳过agent_end/turn_end重复快照，不分配其完整正文；必要事件仍有大小限制，最终成功仍需agent_settled。

另一个缺陷发生在一次大读取把用量从准备阈值以下直接推到交接预留区以上时。旧turn_end同时要求超过准备阈值、低于repairBelow，因此该区间被跳过后不再启动交接。CPU-A在16:45最后一次换窗后增长到约91万输入，直到实际上下文拒绝。修复在阈值以上始终启动有界交接，并阻止继续项目读取；reload后已有过大窗口也适用，人工取消与有限准备次数保留。

旧笔记context钩子在历史之前放入动态index和带当前token数的提示。index变化、越阈值后的每个用量变化都会改写这个靠前的消息，长历史因而无法保留同样的缓存前缀。新版将可变信息放到末尾附近，并保持最后一组assistant/toolResult连续；变化前的大历史保持相同顺序与内容。并修复过大窗口继续增长的问题。

新增测试验证的是请求内容的稳定前缀，而非宣称真实中转缓存必定命中。换窗、模型/工具/会话变化、缓存过期、网关路由都可能造成正常冷启动；服务端实现和后台比率不是客户端可保证的。没有设置虚构cache命中标记或额外发送预热大请求。

## 减少维护往返

context_note支持原子批量写；冲突全部回滚，同正文不增加正文版本，显式保存仍刷新覆盖来源。提示明确列出已完整注入的index/handoff版本；详细内容放主题笔记，以稳定名字和历史ID引用。context_history支持统一输出预算的批量查询/读取及继续游标。当前会话的笔记、模式和历史仍在独立memory.sqlite内；不读取目标/任务账本。

可选memberContext为新成员提供notes/300000默认值，主对话保持summary；显式会话设置、重载后的auto选择和学习到的更低上限保留。避免失败后新成员身份静默回到默认summary。旧笔记不会作为新身份的已完成证据自动导入。

## web兼容核对

本机hosts的Steam++段将github.com及raw.githubusercontent.com映射为127.0.0.1，本地443由Steam++.Accelerator.exe监听。旧插件在连接前拒绝；普通Node HTTPS另报证书链无法验证。逐请求合并系统信任后TLS验证通过。新版实际web_fetch成功读取截图的GitHub LiteX blob链接；同次raw域名返回上游502，不能把传输兼容修复说成远端永不失败。

兼容只接受用户精确配置的公共域名、HTTPS 443与回环解析。直接本地URL、LAN、其他端口及重定向内网仍拒绝，连接固定已检查的解析地址。证书验证不关闭，不修改系统hosts、全局CA或启动参数。Windows实链路、Windows/WSL离线网络策略和原进程reload均需验证。
