# 工作区改名验证与 2.5.3 修复

日期：2026-10-23，Asia/Shanghai。基线：插件 2.5.2、Pi1.4.0，commit `0c7dd7996c39263ffb3175e2749d2048b3b8ccd3`。所有改名、进程控制和故障测试只在临时项目及专用 WSL 回归会话进行；没有操作用户硬件/软件仓库或其生产对话。

## 正确操作顺序

目录还保持原名时，在正在使用它的 Pi 对话输入：

```text
/project rename "新文件夹名"
/project status
/mission resume
```

`rename` 会自己改目录名、暂停成员执行、建立保留历史的延续会话并重建新 cwd 的原生工具。这里不应先去资源管理器手动改名。先手工改名会使旧 cwd 不存在，`switch` 不能猜测这是否同一个项目或自动扩大成员权限；需要恢复旧名字，再从 Pi 执行 `rename`。

`/project switch "另一个已存在的目录"` 是另一种操作：切换主对话工作区，不移动原目录，也不改成员原有工作区授权。改名则映射原目录内成员路径，保持其读写/执行权限不变。迁移后目标与提醒保持暂停，核对后才恢复。已停止的成员任务不会自动重放。

Pi 的延续会话会有新的 session ID，并带原会话来源；它继承原消息和任务身份。新目录 `pi -r` 能发现延续会话。旧历史正文里的绝对路径不被全局改写，必要时用 `project_resolve`/`/project resolve` 映射旧路径。

## 发现和修复

现有工作区相关 11 项回归在 Windows、WSL 均通过。进一步加入笔记模式和压缩模型的测试后，发现两种迁移都遗漏独立的 context-memory SQLite 及运行目录顶层的摘要设置/缓存。这会把新延续会话的 notes 模式变回 summary，或使显式摘要模型退回默认路由。

2.5.3 在原会话空闲、成员已收束的迁移准备阶段：

- 用只读连接的 SQLite `VACUUM INTO` 对本会话记忆库生成一致性副本，包含已提交但仍在 WAL 中的数据；保留笔记正文、revision、source、历史、分页密钥、模式、输入预算与 repair 状态。
- 复制已有的主对话/成员默认摘要路由文件、诊断和摘要缓存。成员 session ID 保持原样，其会话目录内配置仍由原迁移流程保留。
- 不读取其他插件数据库；记忆模块本身仍不依赖目标/团队账本。迁移协调器只为本插件明确延续的会话调用快照函数。
- 在 journal 记录本次创建的记忆目录。原生取消或准备失败时，只删除这次 UUID 延续的副本，原笔记和源库不变；宿主已接管的运行目录不会被当成可回滚删除。
- 旧 cwd 被外部改名时，明确提示恢复原名再执行 `rename`，保持原会话和授权不变。
