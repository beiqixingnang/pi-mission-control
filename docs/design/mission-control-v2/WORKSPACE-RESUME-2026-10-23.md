# 工作区迁移后的一次手动恢复

插件 2.6.1，Pi 1.4.0。修复恢复成功但主界面仍显示推进中、模型将迁移暂停另记为普通目标阻塞、用户恢复后仍不能继续工作的组合问题。

恢复、在线改名和切换工作区完成时，通知明确要求用户在当前 Pi 会话手动执行 `/mission resume`。手工恢复的历史消息也保存这句提示；尚未恢复的既有对话 `/reload` 后再次提示。目标行、窄屏面板和详细视图显示“迁移后待恢复”，并提供恢复命令。`project_status` 显式返回 journal 状态及用户命令；手工恢复中 `renamed=false` 仅表示插件没有执行目录改名，不能推断登记失败。

暂停保持由用户控制。普通聊天、开始新目标、`project_recover` 和模型故障恢复不解除暂停。实际模型的 write/edit/bash/powershell 在此期间统一拒绝，覆盖未建目标、已结束目标和没有子目标的会话；read 等直接读取工具仍可检查历史与文件。

`goal_edit` 可用 `blockedBy:workspace` 明确记录本次迁移引起的暂停；内部标记保存迁移 ID、目标版本、原状态及下一步。原有业务阻塞不能被该标记覆盖。用户手动恢复时，只恢复同一次迁移、相同目标版本与阻塞原因的标记。定义或业务原因已修改、其他迁移的标记、已验收目标、独立业务阻塞及验收证据都保留。未确认前再次移动目录，已经明确关联的标记随延续会话绑定到本次迁移，仍只需一次用户恢复。

旧版没有结构化标记。兼容处理只接受已知控制提示的完整原因，要求持久化 `goal.updated` 事件的版本、状态和原因一致，且该事件在本次 `project.relocated` 之后。包含其他业务内容、迁移前的旧阻塞、缺少事件或原因不明的记录不会被文字模糊匹配解除。截图中的确切原因覆盖在此兼容范围内；不会在 `/reload` 时提前释放，而是在用户执行 `/mission resume` 时处理。

测试只使用临时 agent 和专用“插件回归测试（WSL）”。覆盖原会话热加载、迁移后提醒及状态、旧版阻塞、真实模型写入拒绝与一次用户恢复后的成功写入、多次移动、业务边界与既有证据保留。完整结果及证据哈希见同目录 receipt。生产开发会话由用户自行 `/reload` 和恢复，测试不对它发送命令或修改状态。
