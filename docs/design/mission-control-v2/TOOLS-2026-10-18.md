# 2.0.18 主对话工具暴露与中断执行恢复

日期：2026-10-18，Asia/Shanghai。实现基于本地Pi1.3.0。本文说明当前插件代码，不泛指其他产品的工具发现机制。

## 现场原因

截图中的主模型知道`/mission reconcile`，但没有对应模型工具，无法继续处理四个unknown执行。同时目标已进入`no_progress` attention，旧的通用控制接口只提示用户手动恢复。旧版只激活index内部闭包记录的工具名称，也可能漏掉独立压缩入口以及其他模块直接注册的工具。

命令说明出现在模型上下文中不等于模型拥有调用接口；注册了工具也不等于Pi当前active集合已包含它。这两层需要同时处理。

## 统一名单与直接声明

1. 各模块通过Pi公开`registerTool`注册名称、说明和参数schema。
2. index从`getAllTools()`宿主注册表读取定义，以规范化的来源路径识别本包index与compaction两个入口，排除hidden工具。文件URL、真实路径与Windows大小写统一处理。
3. `session_start`及`before_agent_start`把这些工具并入当前active集合，同时丢弃已不存在的旧名称。旧会话不会继续使用过期的工具schema。
4. Pi直接向模型提供定义。模型无需先调用搜索工具，也不需要自己遍历文件。`mission_capabilities`只是可查询的目录，返回名称、说明、active状态、模块和命令对应关系；可按名称查询完整schema。

当前目录共43项：index入口42项（包含它安装的重连及工作区模块），独立compaction入口1项。这里的统一注册表是宿主注册表，不是另一份手工维护的工具名称数组；新增独立包入口仍需纳入来源范围。成员进程继续使用自己的工具集，不继承全部lead工具。

`mission_capabilities`默认返回全部名称；`includeSchemas=true`且未指定`toolName`时，只展示前5个完整定义以限制输出。查询某项使用`toolName`。目录还返回当前目标id/revision及待核对任务id/epoch，便于下一次精确调用。

## 补齐的模型接口

| 工具 | 行为与校验 |
| --- | --- |
| `mission_reconcile` | 对1–100个不同任务原子校验精确epoch、终态及无live执行；记录调用方检查产物与宿主进程后的结束证据。unknown变stopped，已停止请求可幂等重试 |
| `mission_control` | 只恢复带类型的no_progress attention，要求目标id/revision及检查理由；保留预算起点和已有回合、输出、活动耗时 |
| `team_message` | 复用成员消息实现；运行时steer，空闲时创建受跟踪的新回合 |
| `mission_report` | 设置批准的例行报告间隔，完成/失败维护保持自动 |
| `mission_compact` | 结束当前lead生成，等待收束及宿主idle后请求一次压缩；一次性print/json宿主拒绝 |
| `mission_export` | 复用公开流式导出，支持归档成员；新文件独占创建、不覆盖，取消信号传入逐行读取 |
| `mission_history` | 读取主/成员公开日志，支持归档身份及会话索引；LF分页、有界扫描和返回，过滤私有推理与签名 |
| `mission_capabilities` | 查询宿主注册表对应的可见目录和精确schema |
| `reconnect_config` | status/set共用用户命令实现；不续期持久共享恢复额度 |
| `compaction_model` | status/set/off共用摘要模型命令；lead及未来member设置分开，模型必须已配置 |
| `project_recover` | 只完成与当前会话id及cwd一致的已有迁移journal登记，不创建新授权或解除迁移hold |

没有通用“执行任意斜杠命令”工具。显式用户暂停/停止、预算续期、新工作区授权和交互UI仍使用各自入口；这些限制不会被上述恢复接口清除。

## 中断后的操作路径

1. 查询`mission_status`或`mission_capabilities`，读取准确任务epoch、目标revision和阻塞原因。
2. 检查保存产物和宿主实际进程；若旧执行仍存活，先处理它。确认结束后向`mission_reconcile`提交任务列表及具体检查证据。
3. 目标仍为no_progress时，用`mission_control(action=resume)`提交目标身份、revision及下一步。用户暂停、裁决、预算或工作区hold须走对应控制。
4. 按现有产物决定是否需要`team_resume`明确创建新attempt。旧任务状态和结果保留，核对动作本身不重放命令。

进程核对是caller-attested记录，不是接口独立进行OS扫描或杀进程。事件保存核对主体、epoch和证据。重复取消一个已经终结且没有live终止收据的任务，不再把unknown误记为stopped。

## 验证结果与边界

- 完整`npm test`：159项，155通过、4个显式镜像容器项跳过、0失败，约61.4秒。
- 28个直接源码文件严格类型检查通过；两个入口加载无错误，43个lead工具、5个Mission Control命令及1个独立压缩命令。
- 四个核心回归覆盖批量原子性/epoch/idempotence、live拒绝与unknown取消、恢复保留用量与hold、idle后压缩只执行一次。
- 四个真实Pi离线provider回归验证：实际模型请求中的工具定义及reload刷新；四个中断执行经模型核对/恢复并完成新成员attempt；设置与公开历史/独占导出；模型请求压缩后保存检查点并继续下一回合。
- 最终9项针对性复查全部通过，包含原工作区迁移用例补充的模型恢复登记及暂停保留断言。npm打包dry-run为98文件，包含新工具文档及运行模块，不含本地排查目录或用户auth/models/settings。
- 对现场SQLite使用只读连接及在线backup，检查隔离副本：四条unknown均在epoch2；核对后unknown为0，目标attention→active，回合9、输出13623均保留。副本验证禁止启动worker或模型。

本地证据位于忽略目录`.reference/artifacts/v2/tool-exposure-2026-10-18/`，包括完整测试日志、加载检查和副本核对结果。原会话数据库、原宿主进程状态及硬件任务未被本次验证修改；副本核对不能代替原宿主的进程检查，也不表示原会话已经实际续跑。离线provider验证Pi的实际调用链，不代表任意真实提供方或整夜运行验收。
