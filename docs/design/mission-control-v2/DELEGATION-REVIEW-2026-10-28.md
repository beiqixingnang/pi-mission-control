# 软件主对话的委派与提示词调研（待讨论，未实现）

范围：北京时间 2026-10-28 的“软件仓库开发-新”主对话，重点核对用户纠正、公开回复和实际工具调用；不读取私有思考。检查截止于当天 15:50 左右的已保存记录。以下是方案，不属于 2.7.0 的实现内容。未修改运行中的对话、提示词或成员权限。

目前插件并非完全缺少提示。runtime/guidance.ts 已要求根据任务决定权限/期限、避免无关的重复核对；member.ts 也写明能力允许时不能让 lead 代跑常规测试。问题在于这些指导较宽泛，没有把用户这次指定的职责边界转成稳定的协作规则，也没有将真实能力差异解释清楚。

建议分两层修改，不把这次迁移功能混进去。

第一层是现有提示词与工具说明，优先做：

1. 主模型明确保留用户规定的执行/审查/验收分工；“机械落盘”“只补一次测试”仍然属于执行，不因为措辞不同而自动成为主模型职责。遇到成员能力缺口先指出具体缺口，按既有授权修正能力或给出可执行交接；不要默认转给主模型处理。
2. 配对成员之间直接发送常规意见、反例和修复结果。lead 只接收批次可验收交付、真实阻塞、范围冲突和不可自行决定的问题。消息说明区分 note 与 assign，避免把一般沟通或进度提醒又建成一轮执行任务。
3. 将完整已规划清单一次分配给每条线。成员在授权批次内连续推进，完成一个小节后不必等 lead 再逐条派发；保持每个目标和证据对应，但一次合并提交多个叶节。真正依赖或范围变化仍按原规则处理。
4. 默认复用有效审查和测试证据。lead 读取短批次交付及验收依据即可，不因“我要确认”重复运行同一矩阵；新反例、变更或证据冲突才触发相应增量检查。不能以减少维护为由跳过实际验收要求。
5. 频率类要求先区分“内部计划检查”“用户进度汇报”“完成/失败事件”。用户只要求降低其中一项时，不擅自改变其余节奏。不能把“降低干预”直接等同于“改成一天汇报一次”。
6. 成员身份展示和调度以实际 model 字段为准；旧成员保留历史不等于继续派发旧模型。模型调整时说明哪些旧任务在收尾、哪些新任务已换模型，避免用名字代替状态核查。

第二层是能力与调度机制，需要单独决定：

- **已确认的写入冲突。** extensions/workspace/policy.ts 的 WorkspaceAccess.authorize 对 write/edit 遇到 `.agents` 路径统一拒绝，和成员自己的 read-write 设置无关；主模型却把测试/证据安排在该目录。文件工具拒绝是真实的，提示模型“工具都开放了”也不能解除。不要让模型换用 shell 绕过守卫。可选方案：给每条线明确授权的产物/测试目录，或精确开放本项目指定子目录，继续保护 agent 配置、其他会话和 Git 元数据。推荐先设计最小工作目录授权，再用真实成员读写回归验证。
- **审查不等于禁止执行测试。** 13:07 的四个 Terra 被设置成 read-only + files，因此只有读文件的能力，不可能承担用户交给它的常规验证执行。若任务需要跑测试，应按用户授权配置能完成验证的执行环境与输出目录；只读源码、可写输出、可执行命令是不同能力，不应由 reviewer 名称一刀切。
- **四对成员不等于八个有效槽位。** 当前默认 maxParallel=4，八个身份和消息任务不自动带来四条顺畅流水线。建议先减少多余任务与互相等待，再根据配对执行方式和实际资源决定并发，而不是无条件增加成员或线程。
- **唤醒策略需要区分用途。** 当前 reportIntervalMs 控制周期性进度事件，任务交付又会独立唤醒。后续可增加批次交付、相同状态去重和计划检查的独立节奏；需要验证不会漏掉失败或让授权任务无人接续，不能只写一句“每小时再看”。

若认可，建议后续分成两个可验收改动：先修 `.agents`/测试输出能力冲突与任务交接说明；再优化配对持续执行和消息/检查节奏，同时补对应主模型指导。不要新增另一个“提示词插件”，也不把所有角色固定为某个具体模型名称。现有目标数据库、验收记录与工具体系继续复用。
