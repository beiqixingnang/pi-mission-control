# 上下文候选版补充验证（2026-10-20）

候选分支为 `codex/context-modes`，承接 `d303b74`。正式安装仍为 `b6aaad0` / 2.3.1；本轮未安装、重载或测试用户的硬件开发会话。全部交互测试使用专用 WSL 会话“插件回归测试（WSL）”，ID `85289420-ef5b-472a-82ca-5387b6998102`。

## 实际优化

- 笔记模式的输入预算扣除最大输出及安全余量，在剩余预算的75%开始交接。例如1050000窗口、128000最大输出对应889232本地输入预算、666924准备阈值。它是保守策略，不是提供方的实测窗口。预算按本会话、模型及端点隔离；手工覆盖、观察到的上下文拒绝在reload后保留。429、TPM或配额错误不降低窗口预算。
- 工具批次完成后准备笔记，保留模型自行填写的短入口和交接。最多两次补充提醒、八个准备回合；计数跨reload保留。缺少或过时交接时保留原历史，仍有余量才请求修复；取消、已过满或修复耗尽时停止，不自动改用默认摘要模型。
- `context_rollover`通过Pi回合边界写入检查点并继续同一次运行，中间不产生任务结束的settled事件。原先“先settled再空闲换窗”的方式可能使受管成员提前结束，现已加入真实RPC成员回归。切点读取宿主近期保留量并使用Pi原生算法；内存保存的机械调用/回执不再让交接被误判为过时。
- 反复忽略准备请求、只说“准备好了”或继续调用项目工具时，有限修复后通过Pi消息错误接口报告失败；受管成员会标为失败，避免成功的空结果。
- 最多1500估算tokens、最近三条真实用户消息的原文首尾节选随笔记保留，带原始消息ID和截取标记。较晚的用户明确纠正优先于工作笔记。`context_history role=user`可只搜索真实用户消息，避免错误的模型说法和摘要反复影响检索。
- 摘要不再将旧检查点塞回大段新源码分块。先独立缩减本轮新历史；旧摘要加新摘要仍在输出预算内时直接按时间追加，原文保留旧检查点，不额外请求模型改写。只有合计超过预算，才对较短的检查点做合并压缩。原始历史、旧检查点及分块缓存均保留；修订旧检查点不需要重发未改变的源码块。

压缩只读取当前Pi分支的公开历史、自己的记忆库以及宿主压缩设置；不读取目标、验收或任务插件账本。完整目标规划规则沿用前一候选：执行前登记完整清单，执行中增改范围先与用户讨论，滚动规划限于经讨论的从零探索或最终要求未明确的任务。

## 真实6luna验证

使用已有 `gptcodex/gpt-6-luna` API线路；凭证由Pi直接只读引用，未复制或写进报告。仅发送合成源码与测试会话历史，不发送硬件仓库源码。

本轮先做真实Pi文件读取，再单独做近百万材料的运行时对比，二者的范围不能混淆。

### Pi原生文件读取

16个合成TypeScript文件，每个约41KB、578行，低于原生单次读取的字节/行数上限。模型必须先实际调用原生read，再逐文件记录独立随机标识、初始常量和指定边界问题。分两阶段，在同一会话中reload；最后核对早期事实、纠正后的标识、revision、未验收状态和续点。保存笔记由模型自行完成。

用户原文保护改动前的完整复测为67次请求、460.356秒、五次换窗，14项终态检查通过。中间一次把469b误写回4698，最后经历史检索修正；不能把“最终正确”说成“从未出错”。保留该记录用于解释后续优化。

另做定向故障注入：将工作交接故意写成旧ID和revision 1，真实用户已明确纠正为469b和revision 7。强制将原始用户纠正移出近期原文，然后换窗、reload，要求从实际用户消息恢复。6次真实请求、37.778秒，全部9项检查通过。这个探针故意写入错误工作笔记；它不用于证明模型自己生成笔记的质量。

加入用户原文保护后的完整读取复测为64次请求、413.078秒、五次换窗，全部14项终态检查通过。16份原生读取、同会话reload、早期常量、正确ID/revision及未验收状态均验证通过。原文保护避免了该轮复现旧ID回写。

该轮仍出现四次未成功的工具调用，已查明：一次登记在准备换窗时被正常暂缓；两次测试器把相对路径按进程目录解析；一次模型在登记最后文件前就请求完结，被完整性校验拒绝。现已将暂缓提示明确为“未执行、未登记，交接后重试该操作”，将测试器路径按Pi工作区解析，并让登记/完结工具串行执行、错误返回精确待办文件。该轮最终补齐了登记，未将重试说成首次成功。

### 同量近百万材料

材料为固定八批源码，`o200k_base`计数986833 tokens，仅是该自定义线路的本地估算。每两批换窗一次；计时含工作读取、记忆维护、四次换窗及最终问答/回查，不含窗口容量探针。

| 流程 | 耗时 | 请求数 | 记忆检查 |
|---|---:|---:|---:|
| 修复前：旧检查点与新源码重新压缩 | 215.504秒 | 39 | 13/14 |
| 中间方案：旧检查点单独送末级模型合并 | 149.167秒 | 31 | 9/14 |
| 修复后：预算内原样保留旧检查点 | 200.100秒 | 35 | **14/14** |
| 笔记 | 156.212秒 | 27 | 14/14 |

**根因及修复证据：**原流程前三次检查点一直保有批次0。最后一轮把这个包含批次0—5的旧检查点混入约64k估算tokens的新源码块，首块摘要只剩批次6；末级合并因此没有旧条目可用。仅把旧摘要移到末级模型合并仍会丢项，不能靠提示词保证模型不删旧信息。最终改为预算内原样保留旧检查点，超限才合并；同量复测恢复14/14。

另用原始工作回复和已完成缓存做零网络回放，逐轮精确重建检查点。四次长度分别1338、2880、4163、5206字符，均低于8192上限；每轮完整包含上一轮原文，分别保有2、4、6、8条批次标识。该回放拒绝任何缓存未命中的模型请求，`checkpoint-replay.json`记录网络请求为0。原文见 `reading-final-checkpoint.txt`。这验证的是实际原文携带，不是仅看最终问答碰巧答对。

基准的success判断也已修正，API流程完成不再自动算作质量检查通过。13/14及9/14的原始失败记录保留，用于核查修复前后差别。

笔记这轮较快，但两组缓存及回查请求不同，单轮结果不能证明普遍更快或费用更低。提供方usage逐请求记录；配置价格为零不能推断真实费用。Pi原生近期保留、边界生命周期另由上面的真实Pi和TUI验证，运行时基准不能替代它们。

本轮没有重新验证1M单请求容量。前轮实际接受过904144输入tokens，950000本地估算的整窗请求被拒绝，1050000配置上限未被验证。累计处理986833材料不等于一个请求装满1M。
