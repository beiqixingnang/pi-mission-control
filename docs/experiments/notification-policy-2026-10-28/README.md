# 主模型通知策略（2026-10-28）

基线为 `0569b37` / 2.9.0，候选为 `codex/notification-policy` / 2.10.0。开发与测试在隔离候选进行，实际开发 Pi 对话不参与测试、重载或配置修改。

## 可设置项

主模型直接调用 `mission_notifications`，无需用户输入斜杠命令。设置按会话持久保存，支持查询、部分更新和显式重置；重载、迁移后保留。

| 参数 | 默认值 | 含义 |
|---|---|---|
| `taskSuccess` | `true` | 发给 lead 的任务成功交付是否能单独唤醒 |
| `taskFailure` | `true` | 发给 lead 的任务失败交付是否能单独唤醒 |
| `goalReadyLevels` | `[]` | 哪些精确层级的执行批次收束后通知“待验收” |
| `goalAcceptedLevels` | `[]` | 哪些精确层级的正式目标验收后通知 |

一级是主目标，二级是阶段，三级是具体叶子。空数组关闭该类目标通知；不会因为设置通知层级而授权创建更深的目标。

例如用户说“成功不唤醒，失败唤醒，只在二级批次完成时叫我验收”，主模型设置：

```json
{
  "action": "set",
  "taskSuccess": false,
  "taskFailure": true,
  "goalReadyLevels": [2],
  "goalAcceptedLevels": []
}
```

若用户只要二级目标正式验收后的通知，可将 `goalAcceptedLevels` 设为 `[2]`；“待验收”和“已验收”分别控制，不将一次任务结束冒充业务目标完成。

## 交付与接续

静默结果仍保留在任务账本和产物中。它们可由主模型显式收集，或随原定周期汇报、其他有效通知一起汇总；不被标为已读，不重新执行任务，也不被额外的空闲接续通知立即绕过。汇总沿用既有批量上限，给出未读总数和静默数量；剩余收据继续保留。

向父任务或其他成员的交付照常进行，避免关闭 lead 通知后破坏执行者与审查者的接续。显式授权问题、运行时恢复、定时提醒保留独立机制；任务通知策略不会改变用户指定的汇报频率、预算或暂停状态。已提交但尚未开始的唤醒会按新设置失效重排，已经运行的回复可以收束。

目标待验收要求该批次全部必需叶子有有效验收记录或当前版本的成功任务，相关工作已收束且无未知进程。失败后须显式重试成功才能达到准备条件。同批次去重，叶子验收本身不重复制造准备通知；目标修订、取消、新增工作等使旧通知失效。正式验收通知按验收记录去重。

`notifications.test.mjs` 覆盖独立成功/失败开关、定时汇报、保存结果、父任务接续、精确层级、重试、主目标验收、去重、过时消息、未开始唤醒失效及独立运行时恢复。真实 Pi 测试覆盖主模型设置、重载保留、成功静默而失败唤醒并汇入成功收据；迁移测试确认非默认策略保留。

专用 WSL 已有会话通过真实工具执行成功静默、失败唤醒、二级批次待验收、二级正式验收、三级不通知和原进程字面 `/reload`。离线 provider 是确定性测试夹具，不用于评价真实模型对任意自然语言指令的理解质量。完整结果见同目录 `validation.json` 和 `tui-report.json`。
