# 多目标长任务关联与真实 Pi 工作流验证（2026-10-29）

这次缺口来自真实的 Open-Software-System Pi 对话：四个成员分别负责一个文件，每个长任务覆盖几十个叶目标。派工只绑定了第一个叶目标，成员按后续小节调用 `goal_submit` 时被正确拒绝，因为任务账本确实没有关联那些目标。问题不是成员提交权限应该放宽，而是公开派工接口缺少多目标关联能力。

现在 `team_send`、`team_broadcast`、`subagent`、成员内部 assign 和任务记录都支持 `goalIds`。`goalId` 保留为兼容的主关联；`goalIds` 最多 100 个，必须全部属于当前选中的同一主目标、是可分配的叶目标，并在创建任务时保存各自的 `goalRevision`。任务提示会包含所有关联目标的完整上下文入口，`goal_context(goalId)` 可读取其中任意一个。

成员提交时，`goal_submit` 可以提交任务关联列表中的任意一个或多个目标。每个目标使用自己的 revision、criteria 和证据，目标分别进入待验收；长任务仍继续执行。任务证据、ready 通知、依赖阻塞、接受条件和计划读取均按关联列表工作。未关联的同主目标兄弟叶仍会拒绝，避免从“任务描述包含了它”推导出执行权限。

真实工作流复刻顺序：注册一个主目标和三个文件小节 → 创建一个成员 → 使用一次 `team_send(goalIds:[三项])` 派发一个长任务 → 成员读取三项上下文 → 成员在同一任务中逐项 `goal_submit` → 三个目标分别显示待验收、任务仍保留全部关联 → 主模型可以分别检查和接受。覆盖单目标兼容、批量关联、逐目标 revision、跨主目标拒绝、未关联兄弟拒绝、reload/历史查询和真实 Pi 工具路由。

最终验证：Windows Node 24.16.0 为 406 项、402 通过、4 项平台条件跳过、零失败；WSL Debian 为 406 项、401 通过、5 项平台条件跳过、零失败。真实 Pi 集成覆盖多目标 `team_send` 和批量 `goal_submit`；专用 WSL TUI 复刻同一流程，并在原进程字面 `/reload` 后保持任务关联和提交记录。完整日志保存在本次候选工作树的 `.reference/multi-goal-validation/`。
