## 当前最值得保留的结论

1. **通知、入队、模型看见、开新回合、处理完成不是同一件事。** Codex 有父会话结果通知和邮箱；其 v2 完成通知的 `trigger_turn=false` 与用户期待的 idle 自动唤醒有语义差别。DSH 和 Pi 的唤醒路径要按实际父状态和宿主 API 追链，不能只看工具名称。
2. **当前监督器存在提前检查的明确路径。** `team:job-start → schedule(0)` 会覆盖常规 interval。主日志在配置 1800 秒时出现 18.840 秒的相邻检查间隔，19 次检查紧跟 peer 下游任务 running 状态记录后 30 ms 内出现。源码和日志相互支持；不是所有频繁活动都由主模型主动轮询造成。详情和条件见 Goal/调度章 G2。
3. **文件权限、工具可用性、OS 沙箱和 Git worktree 各自解决不同问题。** 受限成员只有文件工具时无法承担可运行测试的任务；当前host模式还会启用未经workspace路径包装的Pi原生工具，root/access元数据并不对这些入口产生路径强制约束。必须按实际执行入口判断限制是否覆盖子进程、文件、网络和凭据。
4. **目标持久存在不等于当前允许自动继续。** DSH 单列 durable phase 与 process-local activation；pi-goal-x 保存 owner/generation/claim；Codex 在 Host idle 入口检查持久 Goal 和 continuation deferral。本插件也有状态控制，但恢复接口及多套 pending/唤醒状态之间有缺口。
5. **大日志不等于大模型输入。** 所分析主日志的 98.2458% 是重复的 `team-roster` 和 `goal-state` 磁盘快照。模型请求还要经过分支、压缩、上下文编辑、扩展 hook 和 provider 转换；本轮没有录制过去的全部出站请求。
6. **换一个摘要模型不自动解决单次巨大压缩请求。** 需要先核对实际输入选择、序列化、摘要窗口、请求上限、失败处理和回退路径；“GPT 在 DSH 不思考”“DeepSeek 在 Codex 工具失败”等观察尚未通过协议实验定因。
7. **不能把“流式 ZIP”直接当成“1 GB 会话可流式导出”。** DSH 的 ZIP 压缩输出有背压，但单份 session log 在当前实现中仍整体序列化为字符串；Pi 的 HTML 还会对全部 entries 做整体 JSON.stringify/Base64。详情见会话证据章。
8. **交付确认还存在具体的错层和时序问题。** Team普通通知的Pi API追加路径不触发插件监听的扩展message_end，确认标记可能滞后；Goal则在请求后续回合前就主动ACK。两者都不能用单一delivered字段推导模型已消费。

这些结论是固定版本源码和历史日志分析。未运行产品构建、功能测试、故障注入或真实模型兼容性实验；不能视为已经完成长期稳定性验证。

## 如何长期使用本文

- 后续设计应引用专题中的机制、固定提交和不确定项，再作取舍；不要直接把第三方插件的实现当成本项目必须照搬的设计。
- 新实现应另写设计与验收文档。本调查不与实现状态混写，避免“参考项目做得到”被误读为“本插件已经做到”。
- 上游更新后，先核对提交和关键调用链再更新结论；旧日志对应的缺陷应保留版本边界，不能全部算到当前 HEAD。
- 运行实验完成后，补充独立实验记录，明确输入、版本、执行命令、结果和局限；不要倒改这里的“未运行”事实。
- 原始源码、npm 发布包、完整校验数据和私有会话派生证据存放于 Git 忽略的 `.reference/`。本目录正文保留足够的机制说明与版本，阅读理解不依赖保留这次对话；需要逐行复核时再取固定源码。
