# 1.0.1 集成修复验证

目标运行环境为 Pi 1.2.0。修复依据来自四人 CPU/GPU 团队的独立诊断；本次验证没有操作该团队、硬件项目或用户全局配置，也没有运行当前窗口的斜杠命令。

## 修复

1. **受限成员通信工具不可达**：`member-bridge.ts` 改用共享的 `POLICY_ENV` 常量读取 `PI_AGENT_WORKSPACE_POLICY`。受限成员注册 `workspace_team_message`，普通成员注册 `team_message`。即使只在通信对的一方配置 allow，另一方也能使用消息工具；接收权限仍由父进程 ACL 决定。
2. **持久成员 ID 与恢复校验不兼容**：新建持久成员使用 UUID；恢复校验兼容既有、由插件生成的 `team-父会话ID-成员名`，不修改 ID，避免遗失原子会话记录。恢复时先安装完整 roster，再等待各成员启动，并保留历史轮数、最近回复和中断状态。无效快照不会在退出时被空 roster 覆盖。
3. **Goal 与重试冲突**：Goal 在 `agent_before_settle` 的报错边界不立即暂停，允许 retry-any 决定继续；只有最终 `agent_settled` 仍失败时才记录 `pauseCause: provider-error`。重试成功保持 Goal 可执行。监督器把这种暂停识别为可恢复工作，即使没有后台任务仍能周期唤醒；恢复继续使用原预算。用户暂停、blocked、停止和预算耗尽不自动恢复。Goal 状态通知不再把监督检查提前到零延迟。

重试扩展另补了退避期间中断/重载的取消检查，遵守显式 `retry.enabled:false`，并使用 Pi 自身的 transient error classifier 避免两份正则发生偏差。

## 结果

| Windows / Node v24.16.0 / Pi 1.2.0 | 八个入口可加载 | 79 / 79 通过 |

测试命令：

```bash
npm run check
npm test
```

`npm test` 自动建立独立临时 agent 配置。以下场景使用真正的 Pi/Node 生命周期与子进程，而不是仅调用模块内部函数：

- 受限 CPU 监督员与构建员通过消息工具双向交换内容；只设置单方 allow；CPU 到 GPU 的消息在父进程被拒绝，GPU 历史中没有接收到被拒内容。
- 使用旧格式成员 ID 写入记忆，停止全部成员进程，重新打开磁盘主会话并恢复完整 roster，确认旧成员记忆及通信仍可用。
- 完全结束一个父进程，再启动另一个父进程恢复同一份磁盘主会话，确认 parent PID 和 child PID 改变，成员 session ID 与历史记忆保持一致。
- 注入随机 `upstream_error` 后重试成功，Goal 能调用 goal_finish 完成。
- 注入五次 502 后内置重试成功，Goal 状态没有提前暂停。
- 连续六次请求失败（首次加五次重试）后 Goal 标为上游失败暂停；此时没有后台成员任务；监督器下一次检查恢复 Goal 并完成验收。
- 手动标为 blocked 的 Goal 经 provider 重试成功、监督器周期后仍然 blocked。

本次注入错误使用包内的 **离线确定性 provider fixture**，不会访问真实模型 API或消耗模型用量；不是对 DeepSeek 中转站稳定性或 CPU/GPU 硬件成果的验收，也不是对当前终端 TUI 的人工视觉确认。

## 现有会话如何采用

本地路径安装直接指向仓库，代码无需再次复制。当前进程和已启动成员仍使用各自已加载的旧代码；在确认任务已停止、写入已保存后，由用户在该窗口输入 `/reload` 或退出后恢复同一个主会话，才能重新加载修复及启动成员。

旧格式 ID 会原样恢复，不要手动替换快照或重新创建四名成员。可以先检查 team_list，确认数量、权限、通信对、恢复错误和中断状态。现有被标记为 blocked 的 Goal 会保持 blocked；完成必要复核后再明确 `/goal resume`。

监督器在每次重载/重启后默认关闭。由用户按需输入 `/supervisor on 300` 启用五分钟周期；它仍依赖 Pi 进程存活，不提供关机后的后台服务。
