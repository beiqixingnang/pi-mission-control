# Podman sandbox backend

The workspace sandbox runs commands in a local Podman container. The backend requires `execution: "sandbox"` and a `sandbox` object with `engine: "podman"` and an image name or ID. It inspects only the already-local image, parses the full immutable image ID, and uses that ID for container creation with `--pull=never`. It never installs or downloads an image and never falls back to a host command.

Before creating a container, the backend copies a bounded snapshot of the primary workspace into a private temporary directory. It skips `.git`, `.pi`, `.agents`, `node_modules`, `.mission-control`, symbolic links, hard-linked files, and special filesystem objects. Extra read roots are copied below `/reference/0`, `/reference/1`, and so on. The original host directories are never mounted. The container is created with networking disabled, image-declared volumes ignored, a read-only root filesystem, all capabilities dropped, `no-new-privileges`, bounded memory/CPU/PIDs, UID/GID `65534:65534`, and private temporary filesystems. Read-only workspaces and references remain in the read-only image layer. A read-write workspace uses a private container tmpfs and is copied into and out of the container through `podman cp`.

A member timeout may be shorter than the configured `maxSeconds`, but may not exceed it. Container creation also gets a conmon timeout of `maxSeconds + 120` seconds so a killed client does not leave an unbounded container.

A read-write run exports only regular, unlinked files below `/workspace`. Export paths pass the workspace authorization guard, protected runtime/configuration roots, and Windows path checks for ADS, device names, reserved names, and ambiguous aliases. A command cannot write the original read-only workspace or extra roots. Before each export, it hashes the current host files and compares them with the snapshot hashes. A host edit made while the command is running causes the export to fail with a workspace conflict instead of overwriting the edit. Added and changed files are reported in `artifactPaths`; deleted files are also guarded by their original hash. Exported links, devices, and excluded metadata are ignored. Snapshot and export byte counters are enforced while files are read, alongside entry-count, command-output, and timeout limits. A nonzero command still retains its output log and attempts the guarded read-write export before returning `ok: false`.

Each run gets a random container name and a directory at `<workspace>/.mission-control/runs/<runId>`. Exec output is appended to `output.log` through a serialized bounded writer while the command is running, so partial stdout/stderr remains available if the member process exits abruptly. The container carries `run-id` and canonical `workspace-sha256` labels. `inspectSandboxRun(policy, runId)` reads only that run's controlled receipt, derives the private container name, validates both labels, and returns `running`, `stopped`, or `unknown` without starting or cancelling anything. The backend writes this audit metadata even for a read-only workspace; `receipt.json` records state, exit status, container ID, `containerStopped`, errors, and artifacts. The member container receives no writable host path. Cancellation and timeout remove only the run's own named container with `podman rm --force`; `containerStopped: "unknown"` is reported if that cleanup fails. No global Podman cleanup is attempted.

The backend does not inherit host environment variables into the container command. The Podman client receives only the executable search path and the minimal Windows launch variables needed to locate its machine configuration. The image itself still controls its installed command set; a command that assumes `/bin/sh` must use an image that provides it. Podman must already be installed and its machine must already be running. The backend does not provide a host execution fallback. The snapshot and export checks reduce filesystem races, but no user-space implementation can prevent a separate privileged host process from changing the workspace concurrently. The unit tests use a generic placeholder image ID and never start Podman; the real smoke test is opt-in with `PI_SANDBOX_TEST_IMAGE`.
